### VRAM 경계 — 핵심 발견

| 구간 | 모델 크기 | 실측 속도 | 메모리 분배 |
|------|----------|----------|------------|
| **GPU 전부 적재** | 0.5B ~ 8B | 120~631 tok/s | VRAM 100% |

| **RAM 전용** | 103B | 0.1 tok/s | CPU only → 사용 불가 |

### 72B 느린 이유 — 물리적 대역폭 한계

```
토큰 생성 시 전체 가중치를 읽어야 함:
  GPU (VRAM):  16.9GB ÷ 1,008 GB/s = 0.017초  ← 빠름
  CPU (RAM):   32.5GB ÷   58 GB/s  = 0.560초  ← 병목 (17배 느림)
  합계: ~0.58초/토큰 → 이론적 1.7 tok/s
  실측: 1.2 tok/s ← 이론치와 근접, 소프트웨어 문제 아님
```

**결론: 72B Q4_K_M은 이 하드웨어에서 최대 1.2 tok/s. 이건 물리 법칙이다.**

## 4. VRAM 충돌 분석

### 현재 GPU 사용 현황

| 서비스 | VRAM 사용 | 비고 |
|--------|--------:|------|
| Windows + 디스플레이 | ~1.5GB | 고정 |
| 72B 모델 (로드 시) | ~16.9GB | Ollama 자동 관리 |
| Whisper large-v3 | ~3GB | Scheduler 세션 사용 |
| 8B 모델 (로드 시) | ~5GB | 하나씩 스왑 |

### 충돌 시나리오

```
⚠️ 72B + Whisper 동시 사용 시:
  16.9GB (72B) + 3GB (Whisper) + 1.5GB (OS) = 21.4GB < 24GB ← 이론상 가능

⚠️ 72B + Whisper + 8B 동시 사용 시:
  16.9GB + 3GB + 5GB + 1.5GB = 26.4GB > 24GB ← VRAM 초과!
  → Ollama가 72B를 자동 언로드하거나 8B를 RAM으로 밀어냄
```

**권장**: 72B 사용 시 Whisper는 medium 모델(~1.5GB)로 다운그레이드하거나, 시간 분리 운영

```
                ↓

            한국어 특화 → dnotitia/dna:8b (133 tok/s)
            STT → Whisper large-v3 (CUDA, 13x 실시간)
```

### 전략 B: 품질 우선 (배치 리서치)

```
리서치 큐 → 72B (1.2 tok/s, 배치 처리)
              600토큰 응답 ≈ 8분
              비실시간이지만 품질 최고
              야간/대기 시간 활용
                ↓
            8B (후처리/요약/포맷팅)
```

### 전략 C: 균형 (추천 — 32B 도입 시)

```

            배치   → 72B (1.2 tok/s, 야간)

```
